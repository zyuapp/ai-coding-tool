Threadline domain architecture plan

Keep the proven MVP behavior, separate product concepts from Claude, Electron, Git, and localStorage, and break the renderer into feature-owned components without introducing a framework-heavy architecture.

Recommendation: use two core domains—Task and Run—plus a supporting Workspace security/application module. Approval belongs to Run. Git is a Workspace read adapter. Claude is the first coding-agent adapter, not a domain.

Single window One active run localStorage retained No new dependencies

Overview

The MVP already proves folder selection, persisted and resumable tasks, streamed Claude output, permission decisions, cancellation, skills, and changed-file summaries. The cleanup should preserve those user journeys while moving behavior out of the 556-line renderer component and moving Claude SDK vocabulary behind one adapter.

Fixed constraints: Electron, React, TypeScript, the Claude Agent SDK, subscription-backed local use, sandboxed renderer, a separate agent process, and a narrow preload API remain. The architecture must allow a provider replacement without rewriting task storage or presentation.

Out of scope: multiple simultaneous runs, queues, microservices, SQLite, a generic plugin registry, a new state library, a design system, browser automation, Monaco review annotations, installer work, or a second provider implementation.

Behavior change

TodayAfter cleanup
The renderer constructs raw agent requests and interprets provider-shaped events.The renderer invokes task actions and consumes correlated product events. Claude translation ends before the IPC boundary.
A global status, approval, task ref, and worker make stale events able to update the wrong task.Every command and event carries taskId, runId, and sequence; obsolete events are ignored deterministically.
Task stores the Claude session ID, changed-file projection, transcript, mode, and project path together.Task owns conversation history, project association, product-level execution preference, and the persisted opaque Continuation. An active Run uses that Continuation and owns live execution state; change status remains a read projection.
React reads and writes localStorage directly, and malformed data silently becomes empty history.A versioned task repository adapter owns parsing and migration. Corruption is reported and never silently overwritten.
Agent and Git IPC accept renderer-supplied folder strings; the folder picker itself is main-owned.The folder picker returns a main-issued Workspace ID. Later agent and Git commands use that ID, and every payload is checked at runtime.
One component renders the entire product and owns orchestration.A single task-workspace controller owns state; five feature components render it. CSS stays shared initially.

Provider boundary

The coding-agent port accepts a prompt, Workspace reference, execution policy, optional Continuation, abort signal, and Run identity. It yields normalized assistant text, Tool intents, continuation updates, completion, failure, and cancellation. The coordinator and provider execute inside the utility worker; Electron main only brokers validated IPC and worker messages. Only claude-agent-provider.mts imports @anthropic-ai/claude-agent-sdk or maps product policies to Claude's default, plan, acceptEdits, and auto values.

Frontend ownership

useTaskWorkspace is the single controller. It owns durable task state, active Run, selection, drafts, event application, and persistence calls. Components receive data and callbacks. Menu visibility and expanded sections remain presentation state; no state-management dependency is needed.

Requirements

ARCH-01 — Claude SDK imports and SDK-specific values exist only in the Claude adapter.
ARCH-02 — Task, Run, and Workspace types contain no Electron, Git, localStorage, or Claude SDK types.
RUN-01 — Every Run command and event identifies its Task and Run; streamed events use a sequence local to that Run.
RUN-02 — Cancelling or superseding a Run cannot change another Run's state or append to another Task. Only the current Run generation may clear active references or emit terminal state.
RUN-03 — Approval is visible only while its Run is awaiting that decision; completion, cancellation, or replacement expires it.
RUN-04 — Worker exit or transport loss fails the active Run, expires its approvals, and does not become an uncorrelated generic message.
DATA-01 — Existing threadline.tasks.v1, threadline.projects.v1, and threadline.last-folder.v1 data preserves messages, sidebar grouping, last-folder behavior, execution preference, and valid resume capability. A v1 sessionId becomes { provider: "claude", value: sessionId }.
DATA-02 — Invalid persisted data is surfaced and preserved for recovery. Normal write-back remains disabled until recovery or reset; an invalid continuation retains its transcript but is marked non-resumable.
WORK-01 — The folder picker returns a main-issued Workspace ID. Agent and Git operations carry only that ID; main resolves it to a canonical root.
WORK-02 — Approved Projects re-register after restart from persisted entries, with canonical roots revalidated before use. The renderer cannot register a new arbitrary path.
WORK-03 — Path-addressable writes through symlinked or newly created targets are denied when their canonical nearest existing parent escapes the root. Arbitrary shell confinement is never claimed without provider or OS sandbox support.
IPC-01 — Every renderer-to-main payload is checked at runtime before filesystem, Git, or agent work begins.
UI-01 — Existing sidebar, conversation, approval, change summary, composer, modes, and stop behavior remain observable after component extraction.
UI-02 — Feature components do not call window.desktop, localStorage, or provider APIs directly.

Implementation sequence

PR 1 — Passive presentation extraction

Outcome
Sidebar, header/changes, conversation, approvals, and composer can evolve independently before protocol edits touch the same JSX.
Scope
Extract five presentation-only components with data/callback props. Preserve all state and behavior in App.tsx; keep icons and CSS shared.
Abstractions
ProjectSidebar, WorkspaceHeader (including Changes), ConversationTimeline, ApprovalCard, and TaskComposer.
Files
Create five files under src/renderer/components/; reduce src/renderer/App.tsx; update src/renderer/styles.css only if selectors require it.

PR 2 — Correlated Run lifecycle

Outcome
Stale output, cancellation, worker failure, and approvals cannot mutate the wrong Task.
Scope
Add Task/Run identities, per-Run sequence, explicit terminal states, Run-scoped cancel, generation guards, and idempotent expireApprovals(runId). Late terminal events and replies are ignored.
Abstractions
Run, RunEvent, Approval, pure lifecycle transitions.
Files
Create src/domain/run.ts and src/application/task-workspace.ts; atomically replace src/shared.ts with focused domain and src/contracts/ipc.ts contracts; update both tsconfigs, src/main/main.ts, src/main/agent-worker.mts, src/preload.ts, and src/renderer/App.tsx.

PR 3 — Coding-agent port and Claude adapter

Outcome
A provider can be replaced without changing renderer, Task persistence, or Run lifecycle.
Scope
Move SDK setup, permission mapping, Continuation mapping, and stream translation behind the app-owned port. Coordinator and provider remain inside the utility worker.
Abstractions
CodingAgent port, ClaudeAgent adapter, worker-side RunCoordinator, opaque Continuation.
Files
Create src/main/agent/agent-provider.mts, claude-agent-provider.mts, and only the coordinator code needed by the worker; simplify src/main/agent-worker.mts; update domain and IPC contracts.

PR 4 — Workspace and trust boundary

Outcome
Renderer input cannot select arbitrary filesystem or Git targets, and workspace enforcement has defined limits.
Scope
Return Workspace IDs from the picker; re-register persisted Projects after restart; validate IPC DTOs; make projectless scope explicit; canonicalize the nearest existing parent for new paths; separate policy from provider callbacks.
Abstractions
WorkspaceRef, workspace registry/service, tool policy, change reader.
Files
Create src/domain/workspace.ts, src/main/workspace/workspace-service.mts, and git-changes.mts; update src/main/main.ts, src/main/path-policy.mts, preload/IPC contracts, and path-policy tests.

PR 5 — Task repository and renderer controller

Outcome
Task behavior, persistence, and the latest per-Task change snapshot can be tested without rendering the application.
Scope
Move task creation, selection, event application, persistence, and all-key migration out of JSX. Retain localStorage, preserve source payloads before migration, disable write-back on corruption, and keep changed files as a timestamped per-Run read projection so old Tasks do not suddenly show live Project state.
Abstractions
Task, TaskRepository, LocalTaskStore, useTaskWorkspace, Task summary projection.
Files
Create src/domain/task.ts, src/renderer/task-workspace/useTaskWorkspace.ts, and local-task-store.ts; reduce src/renderer/App.tsx to the composition shell; add focused store and transition checks.

Risks and constraints

PriorityRiskPlan response
HighUncorrelated worker events can update the wrong Task; cancel currently emits stopped and then idle.PR 2 introduces Run identity, per-Run ordering, generation ownership, and one authoritative terminal transition from the coordinator.
HighPath containment is lexical and only named edit tools are checked; symlinks or shell actions can escape the stated boundary.PR 4 canonicalizes existing parents and denies known path escapes. Shell confinement remains out of scope without a provider or OS sandbox.
HighIPC accepts arbitrary paths and trusts compile-time types at runtime.Use small handwritten guards at the main boundary; no validation dependency is needed yet.
MediumChanging persisted Task shape can lose resume references or history.Keep a tested v1 reader and migrate to the new schema without deleting the source payload.
MediumA provider-neutral contract may become a speculative universal API.Model only capabilities Threadline uses today. Add optional capabilities or another adapter only when a real provider requires them.
ConstraintThe application intentionally supports one active Run.Model correlation now; add scheduling only when parallel execution becomes a product requirement.
